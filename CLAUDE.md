# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow Rules

- Node version: **24 or newer** (see `.nvmrc`). The server's `.ts` files run directly under Node's type stripping, so they may only use erasable TypeScript: no enums, namespaces or parameter properties, and type-only imports must be marked `type`.
- **Never use m-dashes (—) in UI text or code comments.** Use commas, semicolons, periods, or "to" instead.
- There is no hosting, deploy step, or hosted database. Nothing runs on Vercel or Supabase.

### After every task, do all of these automatically

1. **Typecheck**: `npm run typecheck` must pass. If anything under `frontend/` changed, also run `npm run build`.
2. **README.md**: update only if a change affects how users install or use the app, or adds or removes a major user-visible feature.
3. **Git commit**: commit all changes at the end of every task with a concise message.

## Commands

All commands run from the repo root. This is an npm workspace; `npm install` at the root installs everything.

```bash
npm start          # build the interface, run the server, open the window (first run: in-window setup)
npm run setup      # the same setup in the terminal: the AI model, with `-- google` your own Google client, with `-- microsoft` the Azure app's client ID (writes ~/.tabellar/config.json and the Keychain)
npm run dev        # Vite dev server for the interface, proxying to a running server on :4848
npm run build      # build the interface to frontend/dist
npm run typecheck  # tsc for server/ and frontend/
npm pack           # the npm package: builds the interface and the server (to JavaScript in dist/) first

tabellar open      # open the window of a running server (after `npm link`; same as node server/tabellar.ts open)
tabellar status    # running? which accounts, model, engine level?
tabellar autostart on|off   # start at login via launchd (~/Library/LaunchAgents/com.tabellar.server.plist)
tabellar check     # policy asserts, planted-instruction emails, the first run and Autopilot through the engine, the IMAP provider against an in-process fake IMAP/SMTP server, and a few reply drafts from the configured model, in a throwaway TABELLAR_HOME
```

Set `TABELLAR_HOME` to run against a different data folder (default `~/.tabellar`). The Keychain service is always `tabellar`, so a copied folder reaches the real mailboxes: started from another path than `profiles.home`, it pauses itself and fails its pending sends (`pauseIfCopied`). `db.ts` refuses to open the default folder for anything but the `tabellar` command.

## Architecture

### Layout

```
bin/         tabellar.js, the command: runs server/tabellar.ts in a checkout, dist/tabellar.js in the npm package
server/      one Node process, no runtime dependencies
frontend/    React + Tailwind, built with Vite to frontend/dist, served by the server
docs/        the public home page and privacy policy, served by GitHub Pages (Google's consent screen links to them)
```

The npm package (`files` in package.json) holds `bin/`, `frontend/dist/` and `dist/`, which is `server/` built to JavaScript by `npm run build:server`, because Node does not strip types under `node_modules`. A path to a neighbouring server file goes through `sibling()` in `config.ts`, which picks `.ts` or `.js`; relative imports are rewritten by tsc.

### Server (`server/`)

- `server.ts`: `node:http` on 127.0.0.1 (port 4848 by default). Checks the Host header, refuses foreign Origins, and requires the access token as `Authorization: Bearer` on `/api/*`, `/db`, `/db/rpc` and `/session`. `index.html` is served with the token injected only to browsers holding the session cookie, which is exchanged for a one-time code minted by `tabellar open`. Also runs Google sign-in (`/oauth/start`, `/oauth/callback`), the live event stream (`/events`, server-sent events; a connected window makes the engine's watcher check every 5 seconds), and a 10-second timer that calls `outbox.ts` and `snooze.ts`, and the menu bar item (`menubar.ts`).
- `providers.ts`: the mailbox interface (`Mail`: cursor, changes, moved, list, fetch, headerRows, sent, headers, send, drafts, readDraft, saveDraft, discardDraft, sendDraft, label, modify, sendAs, hasSentTo, attachment, watch, disconnect, an optional `calendar`) and `mail(account)`, which picks the implementation by `accounts.provider`: `gmail` (gmail.ts), `microsoft` (microsoft.ts) or `imap` (imap.ts). Mail is described in Gmail's terms (ids, thread ids, label ids with INBOX, UNREAD, STARRED, SENT). Nothing outside the three modules calls a provider directly. `userCalendar()` is the default account's calendar, else the first account with one. `CHOICES` is what setup and Settings offer when adding a mailbox (Google, Outlook, iCloud, Fastmail, Yahoo, Other). `tabellar check` adds a recorder as `MAILBOXES.fake`.
- `imap.ts`: IMAP and SMTP on node:tls, no dependency. An id is the Message-ID; folders are labels (a copy in the folder; removing a label deletes that copy only while another copy is in the Inbox or Archive, checked on the server, else moves it to Archive); archiving moves to Archive; changes compare the Inbox of the last 31 days with what is stored; IDLE on its own connection wakes the engine's watcher. The app password is a Keychain item; `secrets` is swapped by `tabellar check`.
- `microsoft.ts`: Outlook and Microsoft 365 through Graph (immutable ids, delta queries on the Inbox, categories as labels, Archive, the Outlook calendar) and its sign-in (PKCE, public client, `config.microsoftClientId`, redirect to `http://localhost:<port>/oauth/callback`).
- `mime.ts` (with `bodyOf`, the text and HTML of every inline text part, Gmail's too, and `addressOf`): raw email read (headers, RFC 2047, MIME parts, charsets, attachments, inline images) and written (`writeMessage`, for every provider), and `htmlToText`.
- `outbox.ts`: `sendDueEmails()` sends due `scheduled_emails` (undo send, send later, Autopilot replies) through the account's mailbox. A row with `source` "autopilot" is checked again when due (pause, level, `checkAutoSend` against the stored email it answers, whether the user answered it meanwhile) and kept as a draft if refused. A send that did not reach the mailbox (no network) stays pending for up to 12 hours; one that may have gone out is failed and never repeated. `closeInterrupted()` at start fails what a crash left half done.
- `snooze.ts`: `snooze` archives the thread's inbox mail in the mailbox and sets `emails.is_snoozed` with `snooze_until` (empty: until an answer); `wakeDue` (the 10-second timer) and `wakeThreads` (from `storeInbox`, when someone writes in the thread) return it to the inbox unread. Once back, `is_snoozed` is false and `snooze_until` is when it came back, which counts as needing the user until it is archived, done, answered (`answered`) or snoozed again. Moving it to the inbox in the mailbox ends the snooze. `unsnoozeAll` before an account is disconnected.
- `forward.ts`: `withForward` appends the email handed on (`forward` on `scheduled_emails` and `draft_emails`: `{email_id, without}`) with its attachments, in the outbox, `/send-email` and saved drafts; `messageIdOf` turns the window's message id into the Message-ID a reply answers.
- `receipts.ts`: a read receipt is asked for with `Outgoing.receipt` (Disposition-Notification-To, or Graph's flag) and kept as `emails.receipt_asked`; such mail has `awaits_reply` true, so Follow-ups lists it. A returned multipart/report is recognised by each provider (`EmailData.receipt`), stored with `is_receipt`, sorted without the model, sets `seen_at` on the sent email (`markSeen`), and counts as no answer.
- `prep.ts`: `prepFor` (`POST /calendar/prep`) is the last thread with a meeting's people (`CalEvent.people`) and what is open with them, from stored data; `tellMeetings` notifies once within the hour before a meeting (`profiles.meetings_told`, `notify_meetings`).
- `files.ts`: `GET /files/search` asks each mailbox (`mail(a).files`, optional) for messages with attachments and returns those not kept here. The Files view lists the kept ones from `emails.attachments`.
- `menubar.ts`: the menu bar item, a JavaScript for Automation script run by osascript (macOS only, `profiles.menu_bar`); state goes to its stdin as JSON lines, menu choices come back on stdout, and it ends when its stdin closes. The count is `needCount` in `brief.ts`.
- `sync.ts`: `syncMail(userId, initial)` (which keeps `accounts.history_id` only once what it fetched is stored; a provider's `fetch` skips only messages that are gone and throws on anything else) fetches new mail and applies changes made in the mailbox itself (read, starred, archived, trashed, moved back to the inbox) to the stored copies, both from the mailbox's changes (`mail(a).changes`; the last 30 days, at most 300, when the history has expired); sent mail is fetched when the changes show some or every 10 minutes, contacts (Google only) every 6 hours and `analyzeInbox(userId)` runs the analysis; each is serialised so the window and the engine never overlap. New and sent mail is also counted in the sender statistics.
- `firstRead.ts`: `startFirstRead()`, started when a mailbox is connected or a model chosen (`engine.readNow`), by the window's first fetch and by the engine until done. Headers of the last 90 days (at most 5,000) into `mail_index` and `senders`, with the newest mail sorted meanwhile; beside them, as soon as there is a model, the last 200 sent emails (`learnOnce`: one careful-model call that writes the first `fact` preferences, the role and current work as `Role: ` and `Works on: `, then the style from all of them (`writing.ts`), then `judgeSent`), which go first on the mailbox's quota; then suggested labels; then the last 30 days of inbox mail, people before bulk, 300 in all. Progress in `profiles.first_read`; each step resumes after a restart, and a failure retries on its own with a backoff.
- `automations.ts`: what the user told Tabellar to do from now on (`/api/automations`), one `automations` row per sentence. `compile` has the careful model read it once (`automationFrom` in `ai.ts`) into a trigger (mail, time, silence, meeting), conditions and actions; `checkSpec` refuses anything else, anything its trigger cannot have, and every address, name, word, number or label that is not in the sentence, and `readBack` says in words what will run. A sentence with nothing to do is a `rule` preference. It lands off; `tryOut` keeps what it would have matched in `trial`, and `setEnabled` needs `tried_at` (and makes its label, `categories.automatic` false, which the model is not told of until it has a description). At most one question per email and one `only` per action, answered by the fast model (`answerAbout`), where a yes counts only with a quote found by `rules.quoted`. Mail triggers run in `planNew` before the engine's own planning (`startPass`, `runOnMail`, `endPass`, which archives and marks read in one change), only on mail received since `enabled_at` and once per email; the others from `runTimed`, once a minute (a time missed while the Mac slept runs once, after a sync). Everything goes through `act()` with source `automation` (`action_log.automation_id`). `undone` turns one off after three undos in a row and asks; `archivedByHand` offers one (`questions` options with `automation`). `models` is swapped by `tabellar check`.
- `rules.ts`: what may be made from an email, in code. `todoOf`: only from action-required or important mail, never calendar mail, and only with the model's `quote` found word for word in the email. `meetingOf`: the model copies the time and timezone as written and the sentence they are in; the time is parsed here, from the day the email was sent, and the stated zone (or the user's) applied; `wording` drops dates the model worked out itself from summaries and todos; no quote, a time not in it, or an unreadable zone gives no time. `checkActions` applies both to every analysis. `calendarHeaders` and `parseIcs` tell calendar mail and read its .ics (a `text/calendar` part with or without a filename, kept in `emails.is_calendar` and `emails.calendar_event`).
- `followups.ts`: `suggestedFollowups` (`GET /api/follow-ups/suggested`): sent mail of the last 30 days, two days unanswered, to a person (not the user, a no-reply, list or service address), whose last sent message asks or promises something (`judgeSent`, one fast-model call per sent email, kept in `emails.awaits_reply`), with no `never_followup` preference.
- `senders.ts`: `mail_index` (headers of every message seen) added up per address into `senders`: received, opened, replied, wrote_first, sent_to, archived_unread, List-Unsubscribe, List-Id, Precedence, Gmail category. `profile.ts` reads it to tell whether the user knows a sender; `isBulk()` decides from headers (promotions, or List-Unsubscribe with List-Id or Precedence bulk, never a person or company the user wrote to), and `analyzeEmails.ts` sorts bulk mail without the model.
- `engine.ts`: the background engine, started by `startServer`. A watcher asks each mailbox whether it moved (`mail(a).moved`) every 5 seconds while a window is connected to `/events` and every 20 seconds otherwise (each mailbox on its own; backing off to 5 minutes on errors, 30 seconds with a window open, `engineStatus.mailError` after three in a row, `engineStatus.signIn` for a sign-in no longer accepted; IMAP's IDLE wakes it at once); when it moved, it runs `syncMail` at once and new mail is analysed and planned (`readBacklog` in `sync.ts`: a batch is planned while the next is sorted, so careful-model drafts run beside fast-model sorting). Every 2 minutes (and on the first tick after wake) a full cycle runs as a safety net: sync, analysis, then `planNew`, which turns each newly analysed email (`email_processed.engine_at` null, received within 7 days) into planned actions: a `Tabellar/<Category>` label, a reply draft (action-required, real sender, a question or a reply the analysis thought of, the newest message of a thread the user has not answered since, no draft of the user's own in the thread; written by `replies.ts`), a todo (only what `rules.todoOf` allows), a meeting proposal (only with a time `rules.meetingOf` worked out, and not when the calendar already has an event then or with the sender a day either side; that event is linked in `email_processed.calendar` instead), then `judgeSent` for Follow-ups. When `RULES_VERSION` is above `profiles.rules_version`, stored mail is fetched again once and what older rules made from it is taken back and planned anew. At Autopilot the reply is instead scheduled as a send after `profiles.autopilot_delay_min` (only to someone the user wrote to, when `autopilot_known_only`; the model can answer HOLD to get a draft instead; a reply with a `GAP` left to fill in is always a draft). A pass also takes back what the conversation has moved past (`withdrawStale`: a proposed reply when a newer message is in the thread, a draft the user has not changed when they have answered it themselves) and closes proposals whose time is over (`closePastMeetings`), and a todo another email already made is not made twice (`sameTodo`). Sends macOS notifications for mail that needs the user (action required, or a draft, proposal, meeting or question waiting) or is from a vip, per `profiles.notification_level` and quiet hours, and always for Autopilot replies.
- `policy.ts`: `decide()` is the only place an action is authorised. Levels `observe`/`suggest`/`assist`/`autopilot` (`profiles.autonomy_level`; anything else counts as observe), `profiles.engine_paused`, caps per cycle and per day (Autopilot sends also capped by `profiles.autopilot_daily_cap`), and `looksLikeInstructions()` which limits planted-instruction email to a label. An automation (`decideAutomation`) may label, archive, snooze, mark read, add a todo, draft, notify and place mail in the Brief at any level but Observe, at most 50 actions a day each; in `ask` mode it proposes; making a sender most important is always proposed; it sends (an email handed on) only at Autopilot, on its own, and only to one address its sentence holds (`checkHandOn`, checked again in `outbox.ts`). The engine itself never archives or unsubscribes, and sends only at Autopilot, only in the shape `checkAutoSend()` allows: one recipient who is the email's writer (Reply-To, else From), same thread, no cc/bcc, no attachments. `proposalHash()` binds an approval to the exact proposal.
- `actions.ts`: `act()` decides then does, proposes (status `proposed` with a hash) or logs a refusal in `action_log`; `approve`, `dismiss`, `undo`. The agent's archive goes through `act()` and archives in the mailbox; `setMailState()` (also `POST /api/mail/state`, used by the window and the assistant) archives, unarchives and marks read or unread in the mailbox and in `emails`; agent and assistant sends are recorded. An archive or read with `detail.emailIds` changes (and undoes) a batch in one `mail(a).modify` per account. A draft or send with `detail.forward` hands that email on; its draft has no `email_id`. An Autopilot send becomes a `scheduled_emails` row; undo cancels it while still pending. Everything checks pause.
- `onboarding.ts`: the window's first run after the mailbox (`/api/onboarding/*`). `profiles.onboarding` holds the step, `done` after the last; until then `planNew` plans nothing. `onboardingState` (first read, download), About you, `examples` (about ten todos, meetings, follow-ups and newsletters Tabellar would make, by the rules' own checks) and `answerExample` (Yes, No, Never), `people` and `setVip`, and `finish` (level, the kept labels on mail sorted before they existed, then planning).
- `profile.ts`: what Tabellar knows about the user. `preferences` rows (fact, rule, writing, sender, domain, topic; values vip, normal, quiet, ignore, never_todo, never_meeting, never_draft, never_followup, not_newsletter) and `questions` (at most 3 open, the rest waiting). `profileContext()` is the prompt block (about 400 tokens) for analysis, drafts and Ask; `prefsFor()`/`stops()` let the engine skip what a preference rules out; `knowsSender()` decides when `planNew` asks (`senderQuestion`) instead of making a todo or draft; `learn()` (from approve, dismiss, undo) and `feedback()` (the "Not this" menu) write preferences without a model call; `answer()` applies an answer and re-plans the email, `reopen()` takes one back. `retireTrivia()` keeps `knowledge_base` to people and companies.
- `writing.ts`: how the user writes. `style_profiles` holds greeting, sign-off, tone and length for everyone and, in `kinds`, where they differ for the user's organisation, people they know and strangers (`recipients()`), phrases to avoid (`avoid`), the lines set by hand (`edited`, never relearned) and recent changes to drafts (`edits`). `learnStyle` counts all but the tone from the sent mail (a style from before there were kinds is learned again once, `relearnStyle` in `firstRead.ts`); `learnFromEdit` (`POST /api/writing/edited`, from compose on send) adopts a greeting, sign-off or length changed the same way more than once, in code. Rules are `preferences` of kind `writing`; `isRule` keeps junk out. `writingFor` and `stylePrompt` go into every draft (`draftReply`, `/draft-email` (which is `draftReply` for an answer to stored mail), `/refine-draft` with the rules only, Ask, the agent), and `keepRules` (`problemsIn` for replies) checks the result for avoided phrases and rules like "never open with ...", has it written once more and cuts the sentence if it is still there.
- `newsletters.ts`: the Newsletters view's server side. `listNewsletters` lists senders from `senders` whose mail is bulk by headers (promotions, or List-Unsubscribe with List-Id or Precedence bulk; never the model's category), with at least 2 emails, never someone or a company the user wrote to, and on the user's own domain only with List-Unsubscribe; `unsubscribe` reads List-Unsubscribe fresh from the mailbox and does RFC 8058 one-click (public https hosts only), a mailto (only after the window echoes back the exact address it showed), or returns a web page to open; `archiveSender`; `keepSender`. State in `newsletter_senders`.
- `brief.ts`: `brief()` for `GET /api/briefing`: what needs the user today (drafted replies, proposals, meetings to confirm, todos due, mail back from snooze, unread mail from vip people, open questions, ranked), who they wait on (`followupList`, vip people first), what automations gathered (`digests`), and what was handled, with what was done. An automation can put an email first or leave it out (`email_processed.brief`). No model call. `tellBrief` sends its first three lines as a notification once a day (`profiles.brief.notify`, `brief_told`), after its time and outside the quiet hours, from `tellUser` in `engine.ts`, which runs once a minute apart from the cycle. `briefSettings(profiles.brief)`: `time` ("HH:MM" in the user's zone, when a new Brief starts), `length` (3, 5 or 10 lines a section), `sections`, `summary` and `tone`; `briefDay()` says whether today's time has come and counts what was handled from that time the day before. With `summary` on, `prepareBrief` (the engine's cycle once the time has come, and the window through `POST /api/briefing/summary`) writes one paragraph from those lines into `profiles.brief_summary`; `supported()` throws out a text that names a person or number the lines do not.
- `labels.ts`: the user's labels (`categories`: name, colour, description, `examples` of sender and subject, `position`, `gmail_label`). The model reads them with their examples; mail from an example's sender gets the label in code (`labelsBySender`), bulk mail included. `planNew` applies each in the mailbox (`gmailLabelOf`: the mapped label or `Tabellar/<name>`); `applyLabel` is a label put on or taken off by hand (`POST /api/labels/apply`), which also keeps the email as an example; `suggestLabels` is one careful-model call after the first read's sent step, kept in `profiles.label_suggestions`.
- `accounts.ts`: the mailboxes and the addresses each sends from. `connectAccount()` keeps a mailbox after any sign-in (Google, Microsoft, app password) and makes the profile with the first one. Gmail's "Send mail as" list (other mailboxes: their own address) is read at sign-in and daily into `accounts.send_as`; `defaultFrom` (the user's pick, else Gmail's default), `replyFrom` (the address the email was sent to), `fromHeader`/`fromLine` (the From header; an address the account cannot send from throws). One account `is_default` (new mail, the calendar); a `paused` one is not synced or read. `senders.ownAddresses` counts every account and alias as the user. An account added later gets its own first read (`firstRead.ts`, `accounts.read_at`). Routes: `GET /api/accounts`, `POST /api/accounts/update`, `POST /api/accounts/remove` (`mail(a).disconnect` and deletes its stored mail; the mailbox is not changed).
- `replies.ts`: reply drafts. `draftContext` gathers what one is written from within a budget (`LOCAL` or `CLOUD`): the thread (the stored messages' own words, newest first until the room is used; the quoted text only when nothing is stored), other mail with the same person ranked by shared words, the attachments' text (`fileText.ts`), open todos and meetings with them, and the calendar on the days the email names (only what is with them by name); anything that looks like instructions to an AI is left out. `draftReply(userId, email, said, {kind, auto})` writes it: `said` is what the user wants to say (compose), and without it nothing is decided for them. A decision is left as answers under labels (`choices.ts`). Every draft is checked in code (`problemsIn`: `madeUp` numbers, days, addresses and links, things said to be done, gaps, the user's rules, `decides`), written once more with what was wrong, then the sentence is cut; the sign-off is put there in code (`signedOff`), and an email in another language is answered in it (`languageOf`). The start of the request (the prompt with its examples and the general profile) is the same for every draft and over 1,100 tokens, and a local model is given it alone once (`generateDraft` in `ai.ts`): Gemma reuses a start of that length and recomputes a shorter one, so a longer fixed prompt makes a draft faster, not slower. `sampleReply` (Settings) and `writeTo` (a new email, a follow-up, the note on a forward) are here too.
- `choices.ts`: the answers a draft leaves open, as paragraphs that start with a label in square brackets (`choicesOf`, `choose`, `tidyChoices`). Shared by the server and the interface. The labels match `policy.GAP`, so nothing sends a draft whose choice is open.
- `fileText.ts`: an attachment's text: text kinds and HTML here, Word and RTF through textutil, PDF through PDFKit (osascript), sheets and slides through unzip, each in its own process with a time limit; "" when it cannot be read.
- `drafts.ts`: drafts in `draft_emails` and the mailbox's own Drafts (`gmail_draft_id`). One saved in compose (`POST /api/drafts/save`) goes to both, From the chosen address. So does a reply Tabellar writes, in its thread (`putInDrafts`, from `execute` in `actions.ts`, so at Suggest once approved), unless `profiles.mailbox_drafts` is off or Tabellar is paused; one draft per thread, a newer reply takes the older one's place, and none is added where the user has their own. `syncDrafts` (after every sync) lists the mailbox's drafts: one whose `mailbox_version` changed is read and, if its text did, kept as the user's (`edited_at`: never rewritten or withdrawn); one gone is removed here; one not there yet (made elsewhere, mailbox out of reach) is put there for a day. What the user sent instead teaches `learnFromEdit`. Sending goes through `mail(a).sendDraft` (`scheduled_emails.gmail_draft_id`), which takes it out of Drafts. `discardDrafts()` (`POST /api/drafts/discard`, also undo, Ask and `withdrawAnswered`) takes it out of the mailbox's Drafts too. `outOfDrafts` is the only caller of a provider's `discardDraft`, always with the row's own `gmail_draft_id`; `tabellar check` asserts that, and that the Gmail client's only DELETE is on a draft id.
- `notify.ts` (`worthNotifying` at `profiles.notification_level` vip, needs or none; `inQuietHours` outside the working hours when `notification_quiet`; channels list, macOS via osascript argv), `launchd.ts` (login item), `check.ts` (run by `tabellar check`).
- `api.ts`: `handleApi(req, path)` with all routes under `/api` (fetch-emails, send-email, drafts, briefing, calendar, chat, labels, follow-ups, signatures, agent, ...). `/chat` (Ask) never sends or invites: its `send_email` and `reply_to_email` tools write drafts and `create_meeting` a proposal. It keeps each answer in its `conversations` row makes an automation, off, from "from now on ..." (by code) or the model's `make_automation` tool (always from the user's own words), and starts the cleanup plan (the agent) when asked, by code for "clean up my inbox" and the like or through the model's `plan_cleanup` tool. Written against Web `Request`/`Response`.
- `db.ts`: the SQLite schema (one `SCHEMA` object; columns typed uuid/text/int/real/bool/json/time, defaults filled in on insert, new columns added automatically on start, renames listed in `RENAMES` applied once before that) and `execute(spec)`, which runs supabase-js style queries. Every write is published on `changes` for the event stream. `db.rpc` provides `alloc_agent_turn_idx`, `merge_bucket_draft_actions`, `increment_knowledge_use_count`.
- `query.ts`: the query builder (`from().select().eq().order()...`, `.or()` PostgREST strings, embedded selects like `email_processed(summary)` and `emails!inner(...)`). Shared by the server and the interface.
- `google.ts`: installed-app OAuth with PKCE on the loopback address, through `googleClient()` in `config.ts`: the user's own client when `config.googleClientId` is set, otherwise `BUILT_IN_GOOGLE`, the client that ships with Tabellar. Tokens only work with the client that issued them. Refresh tokens live in the Keychain; `accounts.token_ref` holds only the Keychain item name. Access tokens are kept in memory.
- `llm.ts`: `chatCompletion` takes OpenAI chat-completions requests with a `slot`, `fast` (reading each email in one call: `processFullEmail` sorts and summarises it, suggests todos and meetings, and names the people worth remembering when the user writes to the sender) or `careful` (default: drafts, Ask, the agent, label suggestions). `config.model` is the careful model and `config.fastModel` the fast one, which falls back to `model` when unset. It sends them in that model's `format`: `ollama` (Ollama's native `/api/chat`, so `num_ctx` can be set; no API key), `openai` (forwarded to any OpenAI-compatible endpoint, retrying once without `temperature` or with `max_completion_tokens` when a model rejects them), or `anthropic` (translated to the Messages API and back). Local models get longer timeouts, lower analysis concurrency and batches of 20 (`isLocalModel`, `modelTimeoutMs`); Ollama requests keep the model loaded for 30 minutes, and the fast slot gets an 8,192-token window unless one model serves both slots (a changed window reloads the model). Anthropic content blocks come back on the message as `_anthropic` and are replayed verbatim on later turns so thinking blocks stay intact; the agent persists them in `agent_turns.content.raw`.
- `ai.ts` (prompts and AI helpers), `gmail.ts` (Gmail, Google Calendar and People API client, as `gmailMailbox`), `agentLoop.ts` / `agentTools.ts` / `agentExecute.ts` (the agent: a cleanup plan over the last week of inbox mail, started from Ask), `analyzeEmails.ts` (calendar mail, bulk mail and what `senders.readWithoutModel` allows are sorted without the model; calendar mail is linked to its Google Calendar event; mail from people the user writes to is read first, the email cut to 2,500 characters; mail older than `rules.ACT_WITHIN_MS` is only summarised), `buildBriefing.ts`.
- `setup.ts`: first-run setup shared by the window (`/api/setup/*`, routed in `server.ts` before `handleApi`) and `tabellar setup`: finding and saving the user's own Google client file or going back to the built-in client, the Azure app's client ID (`/microsoft`), adding an app-password mailbox (`/mailbox`, checked against both servers first), installing and starting Ollama (its bundled `ollama serve`, not the menu bar app, whose first launch asks for an admin password), pulling models (with a direct registry download when Ollama can't reach it), and cloud provider key checks. The window's local models are a background job (`startLocalModels`, `POST` and `GET /local`): install, download, then save to the slots.
- `config.ts`: paths, `config.json` (port, the user's own Google client id if any, the Azure app's client id if any, model provider/format/base URL/model), `BUILT_IN_GOOGLE`, Keychain helpers (`keychainGet/Set/Delete`), and `getEnv` for the few settings the backend reads.

### Interface (`frontend/`)

- `src/main.tsx` loads `/session`, then renders `AppShell` + `EmailDashboard` once a mailbox is connected and `profiles.onboarding` is done, otherwise `Welcome`: welcome, mailboxes (`AddMailbox.tsx`, which Settings > Accounts uses too; bringing your own Google client is one link there), model, then in `SetupSteps.tsx` (with the shared `Step` frame and the `Live` progress line) About you, Examples and People, then the level. `#setup` (Settings > General) opens the steps again without holding the engine. `ModelSetup.tsx` has the model panels the model step and Settings > Models share.
- `src/lib/db.ts`: `createClient()` returns an object shaped like the supabase-js client the views were written against: `from()` posts the query to `/db`, `auth.getSession()` returns the local user and access token, `channel().on("postgres_changes", ...)` listens on `/events`. Views keep calling `supabase.from(...)`.
- Global state lives in `AppShell.tsx` via React context (`useApp()`): `user`, `profile`, `view`, `addToast`, compose, the cleanup plan's state (`agentSession`, followed with `adoptSolveAgent` once Ask has started it; the plan renders inside the Ask conversation), and `mail` (below). The shell is a sidebar plus the current view; there is no global top bar, each view renders its own `ViewBar`.
- `src/lib/outcomes.ts`: `useOverview()` loads the action log, drafts, todos, meetings and pending sends once and derives what Tabellar made of each email (`mail.byEmail`), the sidebar counts, the outgoing replies and the engine state, plus `approve`, `dismiss`, `undo`. Inbox rows, the details panel and the sidebar all read from it.
- Undo: `AppShell` keeps ten minutes of changes for Z. A toast whose action is Undo (or Cancel) is one by itself; `pushUndo(label, run)` adds one without a toast. `src/lib/undo.ts` `reversible()` takes back a choice the server spreads over several tables. Global keys are caught on the way down (window capture) before a view's own; a menu that takes the keys is marked `data-key-menu`.
- `src/lib/useLiveUpdates.ts`: one `/events` channel, turned into per-table change counters the views reload on; bumps are handed out at most once a second, so a batch of analysis is one reload a second, not one per row.
- `src/lib/useInboxSync.ts`: a fetch when nothing is stored yet (the first read normally has mail in by then). After that new mail reaches the window over `/events`; a row shows "Reading" until the model has read it.
- `src/lib/appearance.ts`: theme (light, dark, auto), accent, density, text size and hidden sidebar items, kept in `profiles.theme` and `profiles.appearance` and applied to the root element (`data-accent`, `data-density`, the root font size). `useSizes()` in `ui.tsx` gives windowed lists their row heights in px.
- `src/components/settings/`: one file per Settings section, built from `parts.tsx`; `views/SettingsView.tsx` is the section list. Every control saves at once (`useProfile().save`).
- API calls are `fetch("/api/...")` with `Authorization: Bearer ${session.access_token}`.

### Design system

`frontend/DESIGN.md` describes it. The rules that matter when editing a view:

- Colours are tokens defined in `src/index.css` and exposed as Tailwind classes in `tailwind.config.cjs` (`ink`, `ink2`, `ink3`, `canvas`, `side`, `raised`, `hover`, `sel`, `field`, `line`, `wax`, `warn`, `danger`, `ok`, ...). No Tailwind palette classes, hex values or `dark:` variants in components; the tokens follow the theme and the accent (`wax` is the accent, red unless the user picks another). Row, bar and item heights are tokens too (`h-row`, `h-head`, `h-bar`, `h-item`, `min-h-setting`), since density changes them. Lengths are written in px at the default text size and turned into rem by `postcss.config.cjs`; a size set in an inline style must be in rem. Wax red is kept for what needs the user, the one primary action in a region, and outgoing countdowns.
- Shared parts: the component classes in `src/index.css` (`.btn`, `.row`, `.row2`, `.day`, `.bar`, `.pop`, ...) and `src/components/ui.tsx` (`ViewBar`, `Seg`, `Menu`, `Tick`, `Glyph`, `Empty`, `SkeletonRows`, `KeyHints`, `VirtualList`). Long lists go through `VirtualList`.
- Icons come from `src/components/Icon.tsx` (Lucide, bundled); the logo from `Logo.tsx`. Fonts are bundled in `src/assets/fonts`; nothing is loaded from the network.

### Data

One user per install. All tables keep a `user_id` column; the profile row is created when the first mailbox is added. Key tables: `profiles`, `accounts` (one per mailbox, `provider` gmail, microsoft or imap, `server` for IMAP; its send-as addresses in `send_as`, the default account, pause), `emails`, `preferences`, `questions`, `automations` (see automations.ts), `action_log` (what the engine, automations, agent and assistant did or propose, with undo info in `detail`), `newsletter_senders`, `mail_index` and `senders` (sender statistics from headers), `email_processed` (category, summary, quick_actions, `extra_labels` (the user's labels); upsert on `email_id`), `categories` (the user's labels, see labels.ts), `conversations` (Ask), `todos`, `meetings`, `follow_up_reminders`, `scheduled_emails`, `draft_emails`, `style_profiles`, `knowledge_base`, `email_memory`, `contacts`, `agent_sessions`, `agent_turns`.

### Secrets

Never in files, with one exception: the built-in Google client's id and secret are constants in `config.ts`, since Google does not treat a desktop app's client secret as confidential. Keychain items (service `tabellar`): `access-token`, `google-client-secret` (only with the user's own client), `model-api-key:<provider>` (one per cloud provider in use), and one item per connected mailbox: `google:<hash>`, `microsoft:<hash>` (refresh tokens) or `imap:<hash>` (the app password). Downloaded `client_secret*.json` files are gitignored; setup imports them and offers to trash them.
